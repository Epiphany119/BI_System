# 智能 BI 平台 V1.0

## 智能分析任务技术设计

| 项目 | 内容 |
|---|---|
| 对应 PRD | PRD-V1.0-创建智能分析任务 |
| 设计版本 | V1.0 |
| 状态 | 待评审 |
| 文件限制 | 单文件最大 5MB |
| 执行模式 | 同步与异步并存，对用户透明 |
| 同步路由阈值 | 文件大小 ≤ 2MB（V1.0 初始可配置值） |
| 同步失败策略 | 自动重连最多 3 次，单次等待不超过 5 秒，仍失败转入异步 |

## 1. 技术目标

- 将创建分析请求与耗时 AI 执行解耦。
- 使用任务状态机约束任务生命周期。
- 支持自动重试、手动重试、取消等待任务和结果版本。
- 保证重复提交、重复消息和消费者重启不会产生重复结果。
- 保持现有 Spring Boot、MySQL、Redis、RabbitMQ 和对象存储架构兼容。

## 2. 总体架构

```text
React 前端
   │ HTTP / SSE 或轮询
   ▼
ChartTaskController
   │ 鉴权、参数校验、限流
   ▼
ChartTaskService ─────── MySQL
   │                     ├─ chart_task
   │                     └─ chart_result
   │
   ├─ 文件保存 ───────── COS / 本地临时目录
   │
   └─ RabbitMQ
          ▼
   BiTaskConsumer
          │ 幂等检查、状态更新、重试
          ▼
      AiManager
          ▼
      结果持久化
```

同步模式复用任务服务和结果持久化逻辑，但在创建请求内执行；异步模式只在请求内创建任务并投递消息。路由策略由服务端根据文件字节数决定，前端不传递也不展示执行模式。

### 2.1 自适应路由与降级

```text
文件 ≤ 2MB
   ↓
创建统一任务（taskNo、幂等键）
   ↓
同步执行
   ├─ 成功 → SUCCEEDED
   ├─ 连接失败 → 重连 1/3，每次最多等待 5 秒
   ├─ 重连成功 → 继续同步执行
   └─ 三次仍失败 → 原任务投递 RabbitMQ → WAITING

2MB < 文件 ≤ 5MB → 直接创建 WAITING 任务并投递 RabbitMQ
文件 > 5MB → 参数校验失败
```

同步转异步必须使用同一个任务记录和消息幂等键。转入队列前通过条件更新或任务锁保证只有一个执行分支可以继续，避免同步请求与异步消费者并发执行。

### 3.3 chart_task_event

```sql
CREATE TABLE chart_task_event (
  id BIGINT NOT NULL AUTO_INCREMENT,
  task_id BIGINT NOT NULL,
  task_no VARCHAR(32) NOT NULL,
  event_type VARCHAR(40) NOT NULL,
  from_status VARCHAR(20) DEFAULT NULL,
  to_status VARCHAR(20) DEFAULT NULL,
  execution_mode VARCHAR(20) DEFAULT NULL,
  execution_stage VARCHAR(30) DEFAULT NULL,
  attempt INT NOT NULL DEFAULT 0,
  reconnect_count INT NOT NULL DEFAULT 0,
  error_code VARCHAR(50) DEFAULT NULL,
  error_message VARCHAR(1000) DEFAULT NULL,
  duration_ms BIGINT DEFAULT NULL,
  operator_type VARCHAR(20) NOT NULL,
  operator_id BIGINT DEFAULT NULL,
  trace_id VARCHAR(64) DEFAULT NULL,
  metadata JSON DEFAULT NULL,
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_task_time (task_id, create_time),
  KEY idx_event_type_time (event_type, create_time),
  KEY idx_trace_id (trace_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='智能分析任务事件记录';
```

事件类型分为任务生命周期、同步执行、异步执行和用户操作四类。事件表记录关键业务事件和阶段事件，但不保存原始 Excel 内容、完整 AI Prompt、密钥、密码、Token 或完整异常堆栈；`metadata` 单条建议限制在 4KB 以内，完整堆栈进入日志系统。

事件保留策略：V1.0 永久保存 `chart_task_event`，不配置定时清理任务。当前项目数据量较小，永久事件链路便于演示审计、问题排查和简历项目追溯。未来数据量增长后，可在不改变业务接口的前提下增加按月分区、历史归档表、对象存储冷归档或合规保留周期；具体阈值和清理策略另行评审。

结果表不直接覆盖历史结果。重试成功时，新建 `result_version = max(version) + 1`。

## 4. 状态机实现

状态常量：

```java
public enum ChartTaskStatus {
    CREATED,
    WAITING, RUNNING, SUCCEEDED, FAILED, CANCELED
}
```

允许的状态转换：

```text
CREATED  -> RUNNING
CREATED  -> WAITING
CREATED  -> FAILED
WAITING  -> RUNNING
WAITING  -> CANCELED
WAITING  -> FAILED
RUNNING  -> SUCCEEDED
RUNNING  -> WAITING   // 可重试异常
RUNNING  -> FAILED    // 不可重试或超过重试次数
RUNNING  -> CANCELED  // 仅实现可取消时允许
FAILED   -> WAITING    // 手动重试
```

V1.0 不增加 `RETRYING` 主状态。异步重试统一表现为 `RUNNING -> WAITING -> RUNNING`，通过 `retry_count`、`reconnect_count`、`error_code` 和 `execution_stage` 补充过程信息。同步重连期间保持 `RUNNING`；重连次数耗尽后执行 `RUNNING -> WAITING`，并将 `mode` 从 `SYNC` 切换为 `ASYNC`。

所有更新必须使用带旧状态条件的 SQL，例如：

```sql
UPDATE chart_task
SET status = 'RUNNING', started_at = NOW()
WHERE task_no = ? AND status = 'WAITING' AND is_delete = 0;
```

受影响行数为 0 时，表示任务已被其他消费者处理或已进入终态，当前消息应安全结束。

## 5. 接口设计

### 5.1 创建任务

`POST /api/chart/task`

请求类型：`multipart/form-data`

```text
file: MultipartFile
goal: String
name: String?
chartType: String?
idempotencyKey: String
```

校验：

- 登录用户必填。
- 文件非空，后缀仅允许 csv、xlsx。
- 文件大小不超过 5 * 1024 * 1024 字节。
- `goal` 长度 5-500。
- `name` 长度不超过 100。
- 同一用户并发 WAITING/RUNNING 任务不超过 3 个。
- 同一用户相同幂等键直接返回已有任务。
- 服务端根据文件字节数计算 `mode`，客户端不得指定或覆盖该字段。

建议配置：

```yaml
bi:
  chart-task:
    max-file-size: 5242880       # 5MB
    sync-threshold: 2097152      # 2MB，后续压测可调整
    sync-reconnect-attempts: 3
    sync-reconnect-wait-seconds: 5
    async-max-retries: 3
```

上述配置属于非敏感运行参数，放在公共环境配置；API 密钥、数据库密码等仍只放在 `application-local.yml`，不进入 Git。

### 5.2 查询任务

`GET /api/chart/task/{taskNo}`

返回：

```json
{
  "code": 0,
  "data": {
    "taskNo": "AT202609200001",
    "status": "SUCCEEDED",
    "retryCount": 0,
    "resultVersion": 1,
    "genChart": "{...}",
    "genResult": "...",
    "errorMessage": null,
    "createdAt": "2026-09-20T12:00:00+08:00",
    "finishedAt": "2026-09-20T12:00:18+08:00"
  }
}
```

### 5.3 任务列表

`POST /api/chart/task/list/page`

查询条件：状态、模式、任务名称、创建时间范围；每页最多 20 条，只返回当前用户任务，管理员可增加用户条件。

### 5.4 取消任务

`POST /api/chart/task/{taskNo}/cancel`

采用状态条件更新。只有 WAITING 任务可以稳定取消；RUNNING 任务若已进入 AI 调用，接口返回不可取消，不强行中断线程。

### 5.5 重试任务

`POST /api/chart/task/{taskNo}/retry`

仅 FAILED 可重试；创建新的待执行消息，但复用原始文件和分析参数。达到最大重试次数后返回业务错误。

### 5.6 删除任务

`DELETE /api/chart/task/{taskNo}`

执行逻辑删除。删除前校验用户归属；SUCCEEDED 任务的结果按照保留策略处理，默认保留 30 天后清理。

## 6. RabbitMQ 设计

### 6.1 交换机和队列

| 类型 | 名称 |
|---|---|
| Exchange | `bi.chart.task.exchange` |
| Routing Key | `bi.chart.task.execute` |
| Queue | `bi.chart.task.queue` |
| Dead Letter Queue | `bi.chart.task.dlq` |

### 6.2 消息体

```json
{
  "taskId": 10001,
  "taskNo": "AT202609200001",
  "userId": 20001,
  "attempt": 1,
  "traceId": "trace-uuid"
}
```

消息不携带原始文件内容和密钥，只携带任务 ID。消费者从数据库读取任务参数和文件地址。

### 6.3 消费流程

1. 根据 `taskId` 查询任务。
2. 如果任务不存在、已删除或处于终态，确认消息并结束。
3. 使用条件更新将 WAITING 改为 RUNNING。
4. 调用文件解析和 AI 服务。
5. 成功时事务内写入 `chart_result`，并将任务改为 SUCCEEDED。
6. 可重试异常时增加 retry_count，任务回到 WAITING，发送延迟消息。
7. 不可重试异常时写入错误码和错误信息，任务改为 FAILED。

## 7. 重试与错误分类

可重试：

- AI 服务连接超时。
- AI 服务 429 或临时 5xx。
- RabbitMQ 消费过程中的临时网络异常。

不可重试：

- 文件格式错误。
- 文件内容无法解析。
- 分析目标非法。
- AI 返回无法修复的结构化格式错误。
- 用户权限异常。

同步路由失败策略：连接失败最多重连 3 次，每次等待不超过 5 秒；三次均失败后，将原任务切换为 ASYNC 并投递 RabbitMQ。异步任务默认最多自动重试 3 次，延迟 5 秒、30 秒、120 秒；用户手动重试重新进入 WAITING，但总重试次数不能超过系统上限。

同步请求的伪代码：

```java
ChartTask task = taskService.createTask(request, routeBySize(file.size()));
if (task.isAsync()) {
    mqPublisher.publish(task.toMessage());
    return accepted(task);
}

for (int attempt = 0; attempt <= syncReconnectAttempts; attempt++) {
    try {
        return succeeded(taskService.executeOnce(task));
    } catch (RetryableConnectionException ex) {
        if (attempt == syncReconnectAttempts) {
            taskService.switchToAsync(task.getId());
            mqPublisher.publish(task.toMessage());
            return accepted(task);
        }
        sleepAtMost(syncReconnectWaitSeconds);
    }
}
```

实现时必须区分“连接失败”和“业务结果失败”：格式错误、权限错误等不可重试异常直接 FAILED，不得转入异步。同步执行成功后才允许写入结果；转异步前不得写入半成品结果。

## 8. 幂等与一致性

### 8.1 事件类型

```text
TASK_CREATED / TASK_ROUTED_SYNC / TASK_ROUTED_ASYNC
TASK_STARTED / TASK_SUCCEEDED / TASK_FAILED / TASK_CANCELED
SYNC_EXECUTION_STARTED / SYNC_CONNECTION_FAILED
SYNC_RECONNECT_STARTED / SYNC_RECONNECT_SUCCEEDED
SYNC_RECONNECT_EXHAUSTED / SYNC_FALLBACK_TO_ASYNC
ASYNC_MESSAGE_PUBLISHED / ASYNC_MESSAGE_CONSUMED
ASYNC_RETRY_SCHEDULED / ASYNC_RETRY_EXHAUSTED
TASK_CANCEL_REQUESTED / TASK_RETRY_REQUESTED
```

事件不是状态的简单副本：状态表示当前结果，事件表示已经发生过的动作。一个同步任务转异步的完整时间线必须能够通过事件表还原。

- 创建接口通过 `(user_id, idempotency_key)` 唯一索引保证幂等。
- 消费者通过 `WAITING -> RUNNING` 条件更新抢占任务。
- 初始任务必须先落库为 `CREATED`，路由完成后再原子地转为 `RUNNING` 或 `WAITING`。
- 同步转异步使用带旧状态和执行模式条件的更新，确保同一任务只有一个执行器继续运行。
- 结果通过 `(task_id, result_version)` 唯一索引防止重复写入。
- 任务状态和结果写入使用同一事务。
- 数据库事务提交后再确认 RabbitMQ 消息，避免结果未落库时丢失消息。
- 消费者异常退出时，RabbitMQ 重新投递未确认消息。
- 状态变更与 `chart_task_event` 写入必须在同一个数据库事务中完成。
- 统一通过 `transition(expectedStatus, targetStatus, eventType, context)` 执行状态更新和事件记录；旧状态条件更新影响行数不为 1 时，判定为并发冲突并安全结束当前执行分支。

## 9. 安全设计

- 所有任务接口必须登录。
- 所有任务查询必须校验 `task.user_id == loginUser.id` 或管理员角色。
- 文件名只用于展示，文件存储路径使用随机任务目录，禁止拼接用户输入路径。
- 服务端重新校验 MIME、后缀和文件大小，不能只信任前端。
- 日志禁止记录文件内容、密码、AccessKey 和完整模型请求。
- AI 返回内容前端按纯文本展示，避免 XSS。
- 结果下载需要再次校验任务权限和有效期。

日志字段至少包含：`traceId`、`taskNo`、`userId`、`status`、`attempt`、`durationMs`、`errorCode`。

指标建议：

- `chart_task_created_total`
- `chart_task_succeeded_total`
- `chart_task_failed_total`
- `chart_task_retry_total`
- `chart_task_duration_ms`
- `chart_ai_timeout_total`
- `chart_task_queue_depth`

管理员后续可在任务中心查看成功率、平均耗时、失败原因 Top N 和队列堆积情况。

## 11. 测试设计

### 单元测试

- 参数校验器：文件大小、后缀、文本长度。
- 状态机：合法和非法状态转换。
- 重试策略：次数、延迟和错误分类。
- 自适应路由：2MB 边界、同步重连 3 次、单次等待 5 秒及转异步。
- 同步转异步的并发竞态：不得重复调用 AI、不得重复投递有效任务。
- 幂等服务：重复幂等键返回同一任务。

### 集成测试

- MySQL 任务创建和唯一索引。
- RabbitMQ 投递、消费和重复消息。
- AI 成功、超时、429、5xx 和格式错误。
- ≤2MB 文件同步成功并返回结果。
- 同步连接失败 1～2 次后恢复，继续同步执行。
- 同步连续失败 3 次后复用原 taskNo 转入异步队列。
- 转异步期间重复请求和重复消息只产生一次有效执行。
- 2MB 边界值、5MB 边界值和超过 5MB 的文件。
- 任务取消与并发状态更新。

### 接口验收

- 未登录返回 401。
- 越权查询返回 403 且不泄露任务信息。
- 超过 5MB 文件返回参数错误。
- 失败任务可以手动重试。
- 成功任务返回图表和结论。

## 12. 上线与回滚

上线顺序：

1. 执行新增表结构和索引。
2. 发布后端任务接口和消费者。
3. 配置 RabbitMQ 交换机、队列和死信队列。
4. 发布前端任务创建和详情页面。
5. 开启灰度用户并观察任务成功率。

回滚策略：

- 前端可以回退到旧的 `/api/chart/gen` 接口。
- 新表保留，不立即删除，避免影响任务数据。
- 停止消费者前先暂停新任务入口，等待 RUNNING 任务完成或进入重试。

## 13. 待评审事项

1. 是否使用现有 `chart` 表兼容旧页面，还是新旧接口同时维护一段时间？
2. 结果保留 30 天是否满足实际需求？
3. V1.0 是否需要 SSE 推送，还是先采用 5 秒轮询？
4. RabbitMQ 延迟消息采用插件、TTL + DLX，还是 Redis 延迟队列？
5. AI 原始响应是否落库，还是仅保留脱敏后的错误摘要？

已确定的 V1.0 路由参数：同步阈值 2MB、文件上限 5MB、同步重连 3 次、单次等待 5 秒、异步自动重试 3 次。2MB 阈值必须保留运行时配置能力，后续依据压测和生产指标调整。

已确定的 V1.0 状态机：保留 `CREATED` 作为任务初始状态；主状态采用 `CREATED / WAITING / RUNNING / SUCCEEDED / FAILED / CANCELED`；不增加 `RETRYING` 主状态；同步重连期间保持 `RUNNING`，重连耗尽后原任务转为 `WAITING` 并切换为 `ASYNC`；执行阶段、重连次数和异步重试次数通过独立字段记录。
